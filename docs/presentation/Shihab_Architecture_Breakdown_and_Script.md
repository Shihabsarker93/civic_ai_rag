## 3. Figure 4.1, Top Band: Offline Preparation and Indexing

### 3.1 Source documents and prepared data

The inputs include official-source PDF, DOCX and HTML material and prepared Markdown or JSON derivatives [text-based versions prepared from documents]. Cleaning and normalization belong mainly to your teammate's explanation.

Your handover sentence:

> "Using the prepared, source-linked documents just described, we build the search structures used by the chatbot."

Offline means before the user's request, not necessarily that every original document was obtained without the internet. The deployed search works over a saved corpus [the collected text], not live government websites on every question.

### 3.2 Per-domain chunks

A chunk is a manageable piece of source text. A domain is a service area: birth/death registration, passport or BRTA.

Structure-aware splitting [splitting with attention to headings, sections and document types] aims to preserve useful units such as a process section, checklist or fee entry. Do not say every chunk has the same length or that every chunk is a complete answer.

Each record has an ID, text and metadata [information describing where the text came from]. JSONL [one JSON record per line] stores these records locally.

Why do this? Retrieving a whole long document would give the model too much unrelated material. Chunks allow more targeted retrieval while IDs maintain source links.

### 3.3 The crucial split: retrieval_text versus content

`retrieval_text` is search-oriented text. It may contain the source text plus aliases [alternative wording] or section descriptors to help matching.

`content` is the source-derived evidence text supplied for answering. It is not a previously generated model answer.

Illustrative example, not a saved source record:

```text
ID: example_licence_test_01
retrieval_text: driving licence examination; test components; source passage...
content: the actual source-derived passage about examination components
metadata: domain, document, section title, available source URL
```

**Must say:** "We separate the text used to find evidence from the evidence used to write the answer."

This helps prevent a search alias from being treated as an official fact. Source-derived content can still contain extraction errors or outdated information; the separation alone does not validate it.

### 3.4 BGE-M3: turning search text into vectors

An embedding [a numerical representation of text] maps the passage into a vector [a list of numbers]. BGE-M3 is the pretrained multilingual model used for this representation.

Why this choice? Bangla questions may express the same meaning with different words. Semantic search [matching meaning] complements exact-word matching. Multilingual support makes BGE-M3 suitable for the Bangla and English terms in the corpus.

We use its dense representation here. Do not claim that every retrieval mode supported by BGE-M3 is used; our keyword channel is a separate BM25 implementation.

**Index building is not model training.** We calculate vectors with an existing model; we do not teach Qwen the corpus through gradient training or fine-tuning.

### 3.5 ChromaDB: persistent local vector storage

ChromaDB stores vectors, chunk IDs, linked content and metadata in domain-specific collections [separate searchable groups]. Persistent means the index is saved on disk and reused.

Why this choice? It supports local vector search and preserves the link from a numerical match back to readable evidence. Chroma does not write the answer.

The local JSONL chunk map also remains important: runtime search returns IDs and the code reconstructs records from that map. The index and chunk corpus must agree about IDs.

### 3.6 BM25 index: the second search structure

BM25 is keyword-based retrieval. It gives importance to matching query terms while considering how common the terms are and how long a passage is.

Tokenization [breaking text into searchable pieces] applies Unicode NFC normalization, removes selected invisible characters and extracts lower-case word/Bangla sequences.

Why keep this beside dense search? Exact service names, technical terms and form labels can be important even when semantic similarity is broad.

The BM25 structure is built from tokenized `retrieval_text` when the retriever loads. It is NOT another vector collection inside Chroma. Its appearance in the preparation band is conceptual; it is constructed at runtime initialization.

## 4. Figure 4.1, Middle Band: Question to Ranked Candidates

### 4.1 User question and selected domain

The user selects the domain and asks a question. The system uses that domain's configured collection. It does not need an exact match to a stored FAQ question.

Example for explanation: "What does the BRTA driving test include?" The selected domain is BRTA, so passport passages are outside that search scope.

Domain scoping [restricting search to the chosen service area] reduces cross-service mixing. It does not remove every irrelevant passage because BRTA itself includes many procedures.

### 4.2 Input/scope checks and normalization

The interface has a Bangla-oriented input policy. A targeted cross-domain aggregate guard [a check for certain questions asking across multiple service areas] can request clarification.

Normalization [making equivalent text forms more consistent] reduces avoidable wording/encoding differences. It is not a separately trained model that perfectly understands intent.

Why ask for clarification? A narrower question can be safer than returning an answer for an unsupported or ambiguous scope. This is a limited rule-based safeguard, not universal ambiguity detection.

### 4.3 Dense search: find passages similar in meaning

The same BGE-M3 encoder converts the question to a normalized vector. Chroma searches for nearby passage vectors and returns up to 20 chunk IDs.

The query and passages must use the same representation so their vectors are comparable. The LLM is not generating an answer at this stage.

Use this simple line: "Dense retrieval searches by meaning, so the question and document do not need identical wording."

### 4.4 BM25 search: find matching words

The normalized question is also searched against BM25, returning up to 20 positive-scoring results. The implementation excludes scores less than or equal to zero, not only negative scores.

Use this simple line: "BM25 gives us a second view based on exact words and service terminology."

The diagram shows two branches. Do not claim simultaneous execution: the inspected Python method calls the searches sequentially.

### 4.5 Weighted RRF: merge the rankings

RRF means Reciprocal Rank Fusion [combining ordered result lists using positions]. Dense and BM25 scores are on different scales, so adding raw scores directly is not appropriate without another normalization scheme.

Our implementation uses rank positions, with dense weight 0.55, BM25 weight 0.45, and smoothing constant 50. It keeps up to 15 fused candidates [passages being considered, not final evidence].

If a passage appears in both lists, it gets a contribution from each. If it appears in one, only that channel contributes. It is not an intersection-only method.

Why choose fusion? Meaning and exact words are complementary signals. Why these exact weights? They are fixed implementation settings with a slight preference for dense retrieval, not experimentally established optimal values.

**Do not say:** "0.55 means dense is 55% accurate." It is a ranking weight, not an accuracy or confidence percentage.

### 4.6 Reranking: compare each candidate with the question

A cross-encoder [a model that reads the question and passage together] scores each candidate more directly. The configured model is `BAAI/bge-reranker-v2-m3`.

Dense retrieval encodes passages in advance for efficient searching. Reranking performs a more focused query-passage comparison over the smaller shortlist. This adds computation, so we do not apply it exhaustively to the whole corpus for every question.

If the cross-encoder cannot load, a lexical-overlap fallback [a word-overlap scoring alternative] is available. This is an alternative path, not a second reranker always run afterward.

The selected-evidence route requests up to 15 reranked candidates. Do not confuse the general reranker configuration's top-six setting with the explicit 15-candidate override used before selection.

### 4.7 Birth/death-specific adjustments: distinguish them from shared reranking

The base reranker is shared across domains. Additional hand-written score adjustments are enabled only for `birth_death_registration`.

Example: certain registration how-to questions can give an application-process record a 0.08 increment. Other conditions can add or subtract further amounts. These are rule-based increments, not probabilities.

Separately, correction queries can trigger supplementation with an existing registration correction-fee row [adding stored supporting text]. No new fact is generated by this step.

**Important correction for your talk:** this special layer is for birth/death registration, NOT BRTA. BRTA and passport still receive shared reranking and the shared selector.

Why the asymmetry? The earlier implementation focused on registration and its document-type schema. Applying those exact rules to passport or BRTA would be inappropriate. Equivalent custom rules were not implemented for the other domains. We have not isolated the benefit of these rules experimentally.

Good defense sentence:

> "The core pipeline is shared. These additional rules are scoped to the registration schema developed earlier; we did not assume the same rules transfer to other services."

### 4.8 Resolve source content

Matched IDs remain linked to readable content through the local chunk map. The box marks preparation of evidence contexts [passages packaged for the next stage]. It does not mean the program only accesses source text for the first time at this box.

## 5. Figure 4.1, Bottom Band: Evidence to Answer

Point at the bottom-right selector, then move LEFT.

### 5.1 Why selection comes after ranking

Relevance and applicability differ. A passage may mention passports but describe collection rather than a new application. It can be topically relevant without answering the requested procedure.

The selector is a Python function with rules. It is NOT another LLM and NOT a person selecting passages during live use.

It checks recognized service, action, product and location labels. Examples include passport versus visa, replacement versus cancellation, e-passport versus MRP, and domestic versus overseas conditions.

It prefers local section headings to broad document titles when determining scope [which topic or procedure the passage describes].

### 5.2 The selector's actual sequence

1. Identify recognized labels in the question and candidates.
2. Remove duplicate IDs and detected heading-only fragments.
3. Exclude detected service/product/location/action conflicts.
4. Give eligible passages priority for matching action, service and fee/document type.
5. Handle explicitly flagged historical alternatives when appropriate alternatives exist.
6. Avoid merging incompatible alternative checklists under the implemented conditions.
7. Expand eligible fee/checklist continuations from the same document and compatible section family.
8. Group compatible continuations near their anchor passage before applying the budget.
9. Select whole chunks within the passage and character limits, recording decisions.

These are heuristic rules [practical hand-written checks, not guaranteed understanding]. Unrecognized wording and mixed-content passages can still cause omissions or irrelevant selections.

### 5.3 Compatible-section expansion and ordering

A section family [related sections under the same document and parent heading] can contain several fee categories or pieces of one checklist.

Expansion retrieves eligible related chunks from that family. It is not unrestricted retrieval of arbitrary text and does not rewrite source facts.

Grouping places related continuations near the first eligible anchor before the limited context is filled. Otherwise, a continuation appended at the end could be excluded while unrelated candidates occupy the budget.

This is the ordering fix, not a promise that rearranging evidence solves every error. The working thesis reports that replaying 30 saved candidate sets changed selected IDs for the passport-fee question and left the other 29 selections unchanged.

### 5.4 Whole-passage context budget

The selector allows at most SIX passages and at most 14,000 characters of evidence text in total.

Context [the information supplied to the LLM with the question] is different from one chunk. Six is a maximum, not a guaranteed count. Chunks differ in length.

If the next chunk would exceed the limit, the selector skips it rather than cutting it mid-sentence. A later smaller chunk can still fit. This is greedy selection [following the prepared order and accepting what fits], not a mathematical search for the globally best combination.

Why this choice? Limit prompt size and competing material while retaining the full text of each included chunk. A whole chunk can still be only part of a larger document, so do not say the entire procedure is always preserved.

14,000 means characters, NOT tokens. Prompt instructions, source labels and the question add further text beyond this evidence-only count.

### 5.5 Any selected evidence?

If nothing remains, return a clarification/insufficient-information message without asking the generator to create a substantive answer.

If evidence remains, pass it with the question to the prompt. Having evidence does not automatically prove it is sufficient or correct.

### 5.6 Evidence-only prompt

A prompt [instructions and input text sent to the model] requests a Bangla answer supported by the supplied passages. It asks the model to preserve conditions, avoid mixing procedures, and identify missing information.

The selected-route prompt explicitly says that source order is not authority. A first passage is not automatically the correct source for every claim.

"Evidence-only" describes the instruction and intended behavior. It does not technically erase the model's pretrained knowledge or guarantee perfect grounding.

### 5.7 Local LLM via Ollama

Qwen3:8b is the answer-generating language model used in the matched comparison. Ollama is the local serving runtime [software that runs and exposes the model]. LangChain's ChatOllama integration is an adapter [the code connecting the pipeline to that runtime].

Their roles differ: BGE-M3 finds numerical representations; the reranker scores question-passage pairs; Qwen writes the answer.

Generation settings in the documented comparison:

- Temperature 0.05 [low sampling randomness, not an accuracy percentage].
- Top-p 0.9 [limits sampling to a probability-mass-based set of next-token options].
- Maximum output 1,200 tokens [model text units, not words or characters].
- Context window 8,192 tokens [the model's configured working space for the request].
- Repetition penalty 1.18 and repeat window 256 [settings intended to discourage repetition].
- Qwen3 thinking disabled.

These are fixed comparison settings, not proven optimal choices. A low temperature can reduce variability; it does not guarantee identical answers or correct facts.

The inspected registration config still contains an older default model and a legacy three-context setting. The saved comparison explicitly chooses Qwen3:8b, and this selected route uses its own six-passage selector. Explain the evaluated route, not every dormant configuration entry.

### 5.8 Output checks and final response

Language checks can replace unsuitable-language output with a fallback message. A length-based finish reason produces an incomplete-output warning. Source-ID canonicalization [formatting the source list consistently] occurs inside the generator wrapper.

The diagram groups these operations; it does not claim they all happen in exactly the pictured internal sequence.

The final response can include Bangla text, IDs and available source links. The UI can expose evidence for inspection.

**Must distinguish:** source traceability [being able to inspect supplied evidence] is not claim-level verification [confirming every sentence is supported]. No second model verifies every final claim in this live path.

Legacy controlled-answer branches still exist in the repository, but the evaluated selected-evidence path bypasses them. Do not explain the final system as "template answer first, LLM only if the template fails."

## 7. Your Third Slide: Four Equations, Four Plain-Language Ideas

### 7.1 Vector normalization

\[
v_i=\frac{f_\theta(r_i)}{\|f_\theta(r_i)\|_2},\qquad
v_q=\frac{f_\theta(q)}{\|f_\theta(q)\|_2}.
\]

`q` is the question; `r_i` is searchable passage text; `f_theta` is the embedding model; the denominator is L2 length [the vector's mathematical size]. Dividing makes the nonzero vector length one while retaining its direction.

Simple numeric example: vector (3,4) has length 5 and becomes (0.6,0.8). This is not a real BGE vector, just an explanation.

For unit vectors, squared Euclidean distance equals `2 - 2 * dot product`, which explains its relationship to cosine similarity. Do not say Chroma was explicitly configured for cosine distance: the inspected index builder does not override its distance configuration.

Connection to Figure 4.1: point to the passage and query BGE-M3 boxes.

### 7.2 Weighted RRF

\[
S(d)=\sum_{m:d\in L_m}\frac{w_m}{50+r_m(d)},\qquad
w_D=0.55,\quad w_B=0.45.
\]

`d` is a candidate chunk, `m` is a retrieval channel, `L_m` is that channel's result list, and `r_m(d)` is its one-based rank [first result has rank 1].

This is equivalent to the thesis's expanded two-channel equation, with absent channels contributing zero. The restriction under the sum is important.

Example: dense rank 2 and BM25 rank 5 gives `0.55/52 + 0.45/55 = approximately 0.01876`. This is not a confidence score.

Connection: point to the RRF merging box. Say: "We combine rank positions instead of adding incomparable raw scores."

### 7.3 Applicability priority

\[
h(q,c_i)=3A_i+S_i+2T_i.
\]

The indicators [values that are 1 when a condition holds, otherwise 0] are an action match, service match and fee/document-type match. For one action and service match but no type match, priority is `3 + 1 = 4`.

The type indicator is one combined test: matching both possible categories does not automatically give two separate bonuses. Other filtering and grouping steps also affect final selection.

Why these weights? They prioritize action and requested information type, but were not shown to be optimal through a weight sweep [testing many weight combinations].

**Notation cleanup:** your screenshot uses `h(q_i,c_i)`. Use `h(q,c_i)` to match the thesis and the intended meaning: the SAME question is checked against many chunks. This is a notation issue, not evidence of a different algorithm.

Connection: point to automatic evidence selector. Say: "This is one priority rule within the selector, not a trained correctness model."

### 7.4 Whole-passage budget

\[
|E|\leq6,\qquad
\sum_{i:c_i\in E}\operatorname{len}(e_i)\leq14{,}000.
\]

`E` is the selected set of chunk records; `c_i` is one record; `e_i` is its evidence content. Thus the membership test and text-length function refer to different, related things. Define them this way and the notation is consistent.

Example: 13,500 characters are already selected. A 700-character chunk does not fit and is skipped. A later 300-character chunk can fit if fewer than six passages have been chosen.

Connection: point to the bottom of the selector box. Say: "We keep each included passage whole while bounding the total evidence supplied."

## 8. Choices Versus Tests: What You Can Defend

- BGE-M3: multilingual semantic representation is the rationale; we did not prove it is the best embedding model for all Bangla civic tasks.
- BM25 plus dense: complementary exact-word and semantic signals are the rationale; hybrid did not universally outperform dense.
- RRF: rank-based fusion addresses incompatible raw-score scales; the exact 0.55/0.45/50 settings are not an optimum established by this study.
- Reranking: joint query-passage scoring refines a shortlist; a reranker-only contribution was not isolated by the bundled answer comparison.
- Selection and ordering: relevant-only/distraction diagnostics motivated them; those diagnostics are not proof of general selector accuracy.
- Whole-chunk budgeting: practical control of input size and fragment preservation; six and 14,000 are fixed engineering limits, not experimentally optimal values.
- Local Qwen: local execution and a common generator support a reproducible comparison; local execution is not a guarantee of speed, privacy compliance or correctness.

You do not need to apologize for every setting. Explain its purpose confidently and be accurate when asked about experimental validation.
